# Slice 5 DONE: CORE_1_0 SM 6.0 compute corpus + negatives + the barrier fence-ring fix

## The MVK compute->copy barrier fence-ring fix (the session's biggest bug)
The D3D12-level compute probes (exp3: per-test fresh PSOs, dispatch + in-list
UAV->readback copy) showed UAV readbacks staying exactly ONE COMMAND BUFFER
behind: the copy raced the dispatch and read the previous kernel's data.

Root cause (traced with encoder/fence instrumentation):
- The MVK barrier fences used a slot ring whose ROTATION happened at update
  time (getBarrierStageFence) while the WAIT TABLE captured the pre-rotation
  slot; the per-command-buffer encoding context reset the rotation every
  command buffer, so every update reused the same fence slot.
- The copy's waitForFence referenced a fence already signaled by the PREVIOUS
  command buffer -> the wait returned immediately -> the blit raced the
  dispatch. The MTL hazard tracking does not cover argument-table-indirected
  writes (reproduced in pure Metal: 1/30 stale without a fence, 0/30 with
  updateFence/waitForFence).
- Fix (MVK commit 5b76a2a): the rotation moves to setBarrier() so the wait
  table captures the slot the next updateFence will use, and the slot values
  persist on the DEVICE so the ring advances across command buffers.
- Verification: exp3 probe 5/5 dispatches now read the CURRENT value
  (was 0/5); the CORE_1_0 corpus passes 8/8 consecutive runs.
